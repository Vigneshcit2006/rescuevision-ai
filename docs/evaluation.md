# Evaluation Methodology

This document describes *how* RescueVision AI is evaluated. For the actual
measured numbers and their limitations, see `evaluation/reports/` (the
report generated by `evaluation/run_evaluation.py`) — this file describes
methodology only and deliberately does not restate specific figures that
could drift out of sync with the report.

## Why evaluation is separated from the demo

The `/demo` judge-facing flow (`docs/agent-workflow.md`, `DEMO.md`) is meant
to be watched — it favors a clear, fast, visually legible escalation. The
evaluation framework in `evaluation/` is meant to be *measured* — it runs
the same underlying `VisionPipeline` and `AgentPolicy` components
programmatically and records real numbers, with no demo pacing/sleep
involved.

## What is measured, and against what

1. **Vision detection quality** — the four synthetic scenarios described in
   `sample_data/README.md` (`fire_smoke`, `person_down`, `route_obstruction`,
   `normal`) are run end-to-end through their matching `VisionPipeline`.
   Ground truth is definitional: the three incident scenarios are expected
   to reach a `confirmed` state at some point in the clip; `normal` is
   expected to never leave `none`. Precision/recall/F1/false-positive-rate/
   false-negative-rate are computed **only across this 4-clip set**. This is
   explicitly a small, illustrative sample (n=4), not a statistically
   powered benchmark — there is no larger labeled real-world dataset in
   this project.
2. **Performance** — per-frame OpenCV processing latency (and derived FPS),
   agent policy decision latency, and end-to-end (vision+agent) latency per
   frame, timed directly in Python on the development machine the
   evaluation was run on. These are not claimed to generalize to other
   hardware.
3. **Agent decision correctness** — a decision-table sweep over
   representative evidence dicts (varying state, confidence, and scenario),
   checking the agent's actual returned decision/action against the
   documented policy rules in `docs/agent-workflow.md`, plus the resulting
   human-escalation rate under the configured default thresholds.
4. **Cloud metrics** — AWS processing latency, throughput, resource
   utilization, and cost-per-1000-events are explicitly marked
   `NOT MEASURED` in the evaluation report: no live AWS deployment exists in
   the environment this project was built and evaluated in. See
   `deployment/DEPLOYMENT_STEPS.md` for what a real deployment would
   require to make these measurable.

## Reproducing the evaluation

```bash
python evaluation/run_evaluation.py
```

This requires no AWS credentials and no network access — it exercises the
vision pipeline and agent policy directly against synthetic, in-repository
data. See `evaluation/reports/evaluation_report.md` for the report this
command produces, including its own "Limitations of this evaluation"
section.

## Relationship to the automated test suite

`backend/tests/` (`pytest`) checks *correctness* (does the state machine
transition the way it's supposed to, does the policy never send a
notification below threshold, etc.) as pass/fail assertions.
`evaluation/run_evaluation.py` measures *quantities* (how long, how
accurate, how fast) as reported numbers. Both use the same underlying
synthetic scenarios, since no other labeled data exists in this project.
